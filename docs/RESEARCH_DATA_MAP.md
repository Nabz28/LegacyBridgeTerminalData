# Where the research lives, and how to retrieve it

**Reference card for any agent answering research questions. Verified against the live database
2026-08-09.**

Supabase project `adnubucjlezrtusbicja`. Everything below is in the `research` schema unless
stated. Read this before writing a query; three of the traps at the bottom silently return wrong
answers rather than errors.

---

## Connecting

**Reads** go through PostgREST. You must set the schema header or you will get a 406.

```
GET  https://adnubucjlezrtusbicja.supabase.co/rest/v1/<table>?<query>
     apikey: <service_role>
     Authorization: Bearer <service_role>
     Accept-Profile: research          # Content-Profile for writes
```

**DDL** goes through the Management API at `api.supabase.com/v1/projects/adnubucjlezrtusbicja/database/query`
with a PAT. The direct Postgres host is IPv6-only and will not resolve from most runners.
That endpoint needs a browser-like `User-Agent` or it returns 403 error 1010.

There is a working client at `pipeline/lbc/db.py`. Use it rather than rolling your own.

## The three layers of research

Ask "what does the system think about X" and the answer lives at one of three depths. Go in this
order.

### Layer 1 — `signal`: the atomic findings. Start here.

237 rows, **184 live**. This is what you query for almost every question.

```
id, asof, desk_id, kind, ref, headline, payload (jsonb),
salience (0-100), direction (-1|0|1), dedupe_key, retired, created_at
```

`headline` is a complete, self-contained statement with its numbers in it. You can often answer
from headlines alone without touching another table.

```sql
-- what matters right now
select salience, desk_id, headline
from research.signal
where retired = false and salience >= 80
order by salience desc limit 15;

-- everything on one desk
... where retired = false and desk_id = 'indonesia' order by salience desc;
```

**Always filter `retired = false`.** Retired signals are conditions that have since cleared. 53 of
237 are retired and quoting one is quoting something that is no longer true.

**`salience` encodes confidence as well as importance.** A big unverified finding scores below a
smaller verified one. Do not re-rank on your own judgement of what sounds important.

### Layer 2 — `brief`: the written narrative

7 rows. Long-form prose, already edited.

| kind | what it is |
|---|---|
| `deep` | the full research rounds. The 2026-08-07 row is 54,233 chars and is the main document |
| `flash` | the first full system run, 36,021 chars |
| `morning` / `weekly` / `monthly` | the scheduled cadence, 1-2k each |

```sql
select body from research.brief
where kind = 'deep' order by asof desc limit 1;
```

Use a brief when the question is "explain the whole picture" or "what happened in the research".
Use signals when the question is specific.

### Layer 3 — the published reports

`https://legacy-bridge-terminal-data-umga.vercel.app/research/`

Plain-English front page, plus two detailed reports with every correction table. Point a human here.
Do not scrape it; the same content is in `brief`.

## The assurance field. Read this part twice.

Every research signal carries `payload->>'assurance'` saying how well established it is. **78 of 184
live signals have it.** Ignoring it is the single easiest way to mislead someone.

| value | n | means |
|---|---|---|
| `computed` | 107 | machine-generated by the nightly engine. Not reviewed by anyone |
| `adversarially_verified` | 27 | a reviewer tried to break it and failed |
| `verified_corrected` | 17 | was wrong, now fixed, the fix was checked |
| `challenged_corrected` | 12 | was challenged and required correction |
| `verified_by_desk` | 6 | recomputed directly from source |
| `challenged_survived` | 6 | challenged, held up |
| `verified_and_fixed` | 3 | a tooling bug was found and fixed |
| `verified_full_history` | 2 | checked against the full series, not the shipped window |

Why this exists: across four rounds of review, **roughly two thirds of this system's research claims
failed on first check, and corrections failed at about the same rate as the claims they replaced.**
Eight corrections were themselves wrong.

**Rules when answering:**
- Never present a `computed` or unlabelled signal in the same voice as an `adversarially_verified`
  one. Say "on an unreviewed read" or similar.
- If `payload->>'corrected_by'` is set, the current headline *is* the claim. Do not resurrect the
  original. `payload->>'was_wrong'` explains what changed and is worth quoting when someone asks why
  the answer moved.
- If asked for something high-stakes and only `computed` signals cover it, say the evidence is
  machine-generated and unreviewed.

```sql
-- verified findings only
select headline, payload->>'assurance' a
from research.signal
where retired = false
  and payload->>'assurance' like 'verified%' or payload->>'assurance' like 'adversarially%'
order by salience desc;
```

raw industry packs, they are not queryable from here.

## Four traps that return wrong answers, not errors

**1. PostgREST silently caps every response at 1000 rows** and returns the *first* page. It does not
tell you. Every statistic in the first build of this system was computed on stale windows because of
this. Paginate, and order newest first so truncation costs you history rather than the present.

**2. Never put a percentile or z-score on a growing number.** Loan balances, index levels, turnover,
market cap. A series up 132% sits at the 99th percentile permanently and tells you nothing about the
cycle. Only rates, ratios, shares and bounded series support a percentile. This error appeared in
every research round, including inside a note correcting the error.

**3. Check the calendar before calling a change.** Eid, Ramadan and Lunar New Year move between
months. Two of the most dramatic findings in the whole programme were purely calendar artifacts.
Compare the same month a year earlier before saying anything broke.

**4. Company financials are stale and nothing can refresh them.** Every multiple is struck 24 May
2026, before the 20 May rate reversal fed through. The Indonesian and global tables are also a week
apart. Nothing in the system populates them; they are an external snapshot. Say so when quoting a
valuation.

## Query recipes

```sql
-- the current view on a country or sector
select d.name, di.stance, di.conviction, di.machine_score, di.regime
from research.dial di join research.desk d on d.id = di.desk_id
where di.desk_id = 'indonesia';

-- what changed on a desk recently
select asof, stance, conviction, machine_score
from research.dial_history where desk_id = 'coal-power-fuels'
order by asof desc limit 10;

-- everything the system knows about a topic, best evidence first
select salience, payload->>'assurance' a, headline
from research.signal
where retired = false and headline ilike '%coal%'
order by salience desc;

-- was this ever corrected
select headline, payload->>'was_wrong' why, payload->>'corrected_by' by
from research.signal
where retired = false and payload ? 'was_wrong';

-- is the data behind this answer actually current
select pipeline, status, last_success_at, rows_written
from research.ops_freshness order by last_success_at nulls first;
```

## The one habit that matters

This system's most valuable property is that it publishes what it got wrong. Forty-eight
corrections are in the record, eight of them corrections to corrections. When you answer from it,
carry that through: say how well established a finding is, and say when the system changed its mind.
An agent that smooths over the uncertainty to sound more confident is less useful than the raw
tables.
